## 0. 项目全貌

### 0.1 这是什么项目

**Portfolio-App** 是一个个人作品集网站，但它的本质不是"展示"，而是**"验证一套工程方法论"**。

核心理念：**"我建了什么系统让不会的人也能深度掌握"** — 不是展示会什么知识，而是展示建了什么系统。

三层差异化定位：
- **第一层**（用 AI）：所有人都会，打开聊天框问问题
- **第二层**（配 AI）：少数人会用 Skill/MCP/Memory 等机制让 AI 更好用
- **第三层**（建 AI 系统）：深入理解 AI 辅助工作的底层逻辑，搭建可验证、可复用、可自我进化的系统 — **我们在这一层**

### 0.2 当前系统规模

```
portfolio-app/
├── routes/        18 个 Flask Blueprint（agent, knowledge, eval, papers, trainer…）
├── services/      22 个服务模块（agent_service, review_agent, rag_service…）
│   └── eval/       6 个评估组件（trace_logger, eval_store, eval_engine, llm_judge…）
├── static/js/     20 个 JS 模块（含 5 个 eval 专用）
├── templates/     12 个页面模板
├── data/
│   ├── knowledge/ 10 个结构化知识集（Agent开发/AI课程/Python基础…）
│   ├── eval/      评分/追踪/建议/配置/黄金数据集/审计日志
│   ├── chroma_db/ ChromaDB 向量库（bge-m3 embedding）
│   └── exercises/ 练习题库（选择/编程/闪卡）
│
├── 知识库/         25 领域 200+ 闪卡 + 12 篇 AI 论文 + 精炼笔记
├── 知识管线：      data/knowledge/*.json → knowledge_sync → ChromaDB → rag_service → Agent
└── 自审查闭环：    review_agent（Hot/Warm/Cold 记忆金字塔 + 自动回滚）
```

### 0.3 外部知识资源

项目外部有独立的知识体系：
- **`知识库/`** — 25 个领域的结构化闪卡（方法论/设计模式/工具链），12 篇 AI 论文原文 + 精炼笔记
- **论文管线** — arXiv API → 可信度门禁 → 结构化提取 → 论文数据库
- **错误与修正记录** — 每次重大错误的事后分析，存储在 `知识库/错误与修正与优化/`
- **用户反馈** — 会议记录、使用反馈，存储在 `docs/`

### 0.4 最终目标

这个项目要证明的不是"我会写代码"，而是：**一个人 + AI + 正确方法论，可以连续建造复杂系统而不陷入混乱。**

具体来说：
1. **第四面墙纪律**：先完成再扩展，永远不推半成品。Phase 1(吃透)→2(加能力)→3(打磨) 循环
2. **无限细分**：大问题拆到 AI 能完美解决的小问题，层层聚合
3. **自指改进**：系统能评估"做事的方式好不好"，并自动调整
4. **可复用性**：同样的方法搬到不同领域，成本递减

**评估系统在这个目标中的角色是基石性的：没有它，"自指改进"是一句空话，"可复用性"没有度量，"无限细分"没有方向。**

## 1. 为什么评估系统必须是元模块

### 1.1 当前问题

评估系统（Phase 1-4 建设）已经能跑：采集追踪、计算评分、生成告警、前端可视化。四个面板（总览/模块详情/Agent追踪/元评估）172 个测试全部通过。

但 2026-06-11 的用户反馈指出了系统性缺陷：

| # | 问题 | 根因 |
|---|------|------|
| 1 | 指标太泛化，看不到具体模块和功能 | 评分粒度停留在系统级，没有模块级下钻 |
| 2 | 建议不可点击，探索空间有限 | 建议是自然语言文本，缺少结构化元数据 |
| 3 | 元评估面板信息量严重不足 | 只显示数字不显示详情（"10项过时"是哪10项？） |
| 4 | 评分没有基线，不知道数字含义 | 缺参照系（均值/历史/基线） |
| 5 | 评估系统与其他模块无对接感 | 跨模块联动存在但 Dashboard 不可见 |

**根因总结：评估系统是"可看"的仪表盘，不是"可探索"的诊断工具。它无法回答"因为xxx，所以改/不改xxx"——而这恰恰是它存在的理由。**

### 1.2 重新定位

评估系统不是"又一个新功能"，不是侧边栏的一个页面。它是**元模块（Meta-Module）**——为所有其他模块的决策提供数据依据的基石。

```
评估系统 = 决策依据中枢

问题："为什么要重构 eval_engine.py？"
当前回答："我觉得它太长了"
应有回答："它的复杂度评分 0.45 低于基线 0.7，且最近 3 次贡献者反馈都提到了理解困难。
          具体复杂度分布：_compute_data_completeness (圈复杂度 12)、_build_summary (圈复杂度 10)。
          建议拆分为 3 个文件。历史类似拆分（P0-4 eval-slideout.js）效果追踪显示 +0.12 可维护性改善。"

问题："为什么不加 RLAIF 到 Agent 训练？"
当前回答："暂时没想到"
应有回答："知识库收录了 RLAIF 方法论但代码中 0 处引用（知识-应用差距检测）。
          最近一篇相关论文（arxiv 2503.xxxxx）评级为 credible，但尚未评估适用性。
          建议安排一次可行性评估。"
```

### 1.3 设计原则

1. **决策驱动**：粒度不由数据决定，由决策问题决定。每个模块定义"决策面"——需要回答的决策问题清单
2. **追溯完整**：任何一个分数/建议/告警，都能追溯到原始事件。"因为xxx，所以xxx"的xxx必须有凭有据
3. **双水源**：回顾性水源（已经发生了什么）+ 前瞻性水源（可能应该发生但还没发生）
4. **极低接入门槛**：L0 自动享受，L1 三行代码，L2 深度集成
5. **人工兜底**：创新类建议不自动执行，只摆在你面前。元评估递归在 L2 由人工终止

### 1.4 宪法准则（终裁确立，不可动摇）

#### 准则 1：每一个功能都必须能回答一个决策问题

编码前先问："这个功能帮助用户做了哪个决策？"答案不清晰就不做。

- **指标**：每个指标必须附带其对应的决策问题。不允许"因为能采集所以展示"的指标
- **建议**：每条建议必须附带"如果不处理，可能会导致什么决策失误"
- **探测卡**：每条探测卡必须附带"这个信号如果被忽视，最坏可能导致什么"

#### 准则 2：追溯链是决策依据的信任基础

任何通过评估系统做出的决策，必须能回答三个追问：
1. "这个结论是基于什么数据得出的？"（事件）
2. "这个数据的采集是否完整？"（数据完整度）
3. "如果没有这个数据，结论是否会不同？"（反事实）

三个追问中任何一个无法回答，决策依据即不可信。

#### 准则 3："信号"和"噪音"的区分必须由系统自身完成

系统必须有自指能力——回答"我产出的信号中，哪些被证明有价值，哪些被证明是噪音？"。探测卡的 `recurrence_count` 机制是此准则的落地。连续三次被忽略的信号，系统应自动降低优先级或建议关闭。

#### 准则 4：元评估层级不超过两层

L2 必须是整个系统中最简单的模块——简单到可以由人工在 30 秒内完成检查。如果未来发现 L2 不够用，**不是增加 L3，而是简化 L1**——减少 L1 的检查项，让 L1 简单到不需要 L2 来审视它。

### 1.5 执行最高优先级

1. **决策面覆盖检测提前到 M3**：Dashboard 上必须能看到"已覆盖 vs 未覆盖模块"对比
2. **M2 追溯链必须覆盖断裂链状态**：完整链/部分链/断裂链三态全部验收
3. **L2 必须独立运行**：独立 Timer + 独立日志 + stdout 警告，不被单点故障击穿

## 2. 架构设计

### 2.1 决策追溯链（六环骨架）

```
[1.事件] ─→ [2.指标] ─→ [3.告警] ─→ [4.建议] ─→ [5.决策] ─→ [6.效果]
    ↑                                                        │
    └──────────────── 反馈闭环 ───────────────────────────────┘
```

每个环的输出携带对上一环的引用（`source_event_id → metric_id → alert_id → suggestion_id → decision_id → effect_id`），形成不可伪造的追溯链。

| 环 | 职责 | 当前状态 | 差什么 |
|---|------|---------|--------|
| **1. 事件** | 系统中发生的一切 | `trace_logger` 已有 HTTP/LLM/Tool 三类 span | git 事件、知识摄入事件、用户反馈录入、前端行为追踪 |
| **2. 指标** | 事件聚合为可对比的数值 | `eval_engine` 已算 12 个系统级指标 | 模块级指标、知识管线指标、创新差距指标 |
| **3. 告警** | 指标跌破阈值 → 告警 + 证据 | `_build_alerts()` 已有 | 告警缺少关联证据（"为什么报警"的具体数据） |
| **4. 建议** | 告警+证据 → 可执行建议 | `suggestions.json` + `review_agent` 已有 | 建议缺结构化元数据（关联模块/文件/数据源） |
| **5. 决策** | 采纳/拒绝，记录原因 | `apply_suggestion` / `reject_suggestion` 已有 | 决策原因未记录（"为什么拒绝"比"为什么采纳"更有价值） |
| **6. 效果** | 采纳后 N 天，指标是否改善 | `_effect_tracking_loop` 已有 | 仅追踪采纳过的，不追踪拒绝后是否恶化 |

**追溯链完整性校验：** 每个环的输出在写入时附加 `chain_hash = SHA256(source_event_id + metric_id + alert_id + suggestion_id)`。`evaluate_document_integrity()` 在元评估中抽样检查哈希，不匹配则生成 P0 告警。追溯链不是"不可伪造"——是"伪造可被检测"。

### 2.2 双水源架构

#### 回顾性水源（已经发生了什么）

| 水源 | 当前状态 | 接入方式 | 产出指标示例 |
|------|---------|---------|------------|
| HTTP/Tool/LLM Span | `trace_logger` 已采集 | L0 自动 | 数据完整度、响应时间 |
| Git 提交历史 | 存在但未接入 | `emit_event("git.commit")` via hook | 模块变更频率、热点文件 |
| 测试结果 | pytest 可跑但结果未入库 | CI 后 `emit_event("test.run")` | 测试覆盖率趋势、失败率 |
| Review Agent 发现 | 独立存储 | 统一写入 eval events | 错误指纹重复率 |
| 用户反馈 | 有记录但无录入入口 | `emit_event("feedback.received")` | 反馈响应率、需求覆盖率 |
| 前端行为追踪 | 无 | `navigator.sendBeacon` → `/api/eval/beacon` | 面板使用率、建议点击率 |

#### 前瞻性水源（可能应该发生但还没发生）

**性能约束：** 前瞻性水源的检测涉及全代码库/全知识库扫描，必须作为低频后台任务运行，不得在同步路径（HTTP 请求处理）中执行。每种检测器的性能基线必须在 M5 前建立（见 M5 验收标准）。

| 水源 | 检测逻辑 | 产出指标 | 建议运行频率 |
|------|---------|---------|------------|
| 知识摄入 vs 应用差距 | 知识库有标签 X → grep 代码中是否出现 | `kb_application_gap` | 每日一次 |
| 模块变更停滞 | git log — 超过 N 天无变更 | `module_staleness` | 每日一次 |
| 重复错误指纹 | 同类型错误 ≥3 次 | `error_recurrence` | 每日一次 |
| 外部技术动态 | arXiv pipeline vs 当前技术栈 | `tech_freshness` | 每周一次 |
| 决策面覆盖空缺 | 有模块但无决策面定义 | `eval_coverage` | 决策面变更时触发 |

#### 探测卡机制（前瞻性水源的产出格式）

前瞻性水源**不直接产告警**——它产**探测卡（Probe Card）**：

```yaml
probe_card:
  type: "创新信号"
  source: "kb_application_gap"
  finding: "知识库中有 RLAIF 方法论但代码/文档中 0 处引用"
  severity: "INFO"          # 不是 P0，是信息
  suggested_action: "评估 RLAIF 是否适用于当前 Agent 训练流程"
  auto_decision: false      # 创新类建议必须人工决策
  expires_in_days: 30       # 超时未响应 → 自动关闭
```

探测卡不报警、不催办、不自动执行。**只把"可能的盲区"摆出来。** 答不答、怎么答，是人的事。

### 2.3 决策驱动细度

**铁律：粒度不由数据决定，由决策问题决定。**

每个模块定义一个**决策面**——需要回答的决策问题清单：

```yaml
# 例: data/eval/modules/source_tracer.yaml
module: source_tracer
decision_surface:
  - question: "追溯准确率够不够？"
    metric_id: trace_accuracy
    source_type: retrospective
    data_source: manual_spot_check
    baseline: 0.7
  - question: "跟外部方法比落后了吗？"
    metric_id: trace_method_freshness
    source_type: prospective
    data_source: knowledge_pipeline
    check_method: "知识库中'来源追溯'标签的论文中，未被引用的最长天数"
```

**粒度升级触发器（只有三个条件可以细分）：**

| 触发条件 | 例子 |
|---------|------|
| 告警不够具体（报警了但不知道改哪里） | `code_health=0.6` → 拆成文件级 |
| 有人问了答不了（决策者提了一个当前粒度无法回答的问题） | "安全评分低是因为注入还是泄露？" → 拆分安全指标 |
| 元评估检测到停滞（某个指标连续 N 天不变） | 可能"指标找到了作弊方式" → 加噪声或换维度 |

**停止条件：** 细分到"可以直接改一行代码 / 做一个决策"的粒度时停止。

### 2.4 元评估双层结构（无限叠元的解）

```
L1: 看管道的 Meta-Eval
    监控主决策链六个环的健康度，产出 P0 告警 + 建议
    └─ 被谁看？ → L2

L2: 看 L1 的紧凑自检 (Meta-Self-Check)
    不看 L1 的完整输出，只看三件事：
    ① L1 自己是否在运行（心跳）
    ② L1 产出的告警是否被响应（响应率）
    ③ L1 本身的指标有没有退化（如果 L1 说一切都好但系统明显不好 → L1 坏了）
    
    只产出一个 P-1 状态灯：绿/黄/红
    如果红 → 人工介入（递归的终止条件）
```

**L2 独立运行保障：** L2 以独立 `threading.Timer` 运行（每 2 小时），不与主后台循环共享线程。L2 日志写入独立文件 `data/eval/meta_eval_l2.log`。如果 L2 连续两次（4 小时内）无法完成（超时或异常），`server.py` 在 stdout 打印警告——即使评估系统内部循环崩溃，运维人员仍能看到。

**L2 "告警响应率" 的精确定义：**
- **已响应**：告警被转化为建议 + 建议已被采纳或拒绝（有决策记录）
- **自动恢复**：告警对应的指标在下一个评估周期中自动恢复到正常水平（无需人工干预，但需被记录）
- **未响应**：告警持续超过两个评估周期，既无决策记录也无自动恢复
- 此定义写入 `meta_evaluator.py` 的L2检查函数注释中

**L2 不需要 L3。** L2 职责足够简单（三件事）+ 独立线程 + 人工兜底 = 终止递归。

### 2.5 模块接入协议（三层门槛）

#### L0：自动享受（零成本）
所有模块默认享受。用了 `deepseek_client.chat()` → 自动有 LLM span。Flask 路由 → 自动有 HTTP span。不需要任何改动。

#### L1：3 行接入（极低成本）
在模块的关键节点加 `emit_event()`，获得模块专属指标：

```python
from services.eval.trace_logger import emit_event

emit_event("source_trace.completed", {
    "query": user_query,
    "steps_completed": 6,
    "duration_ms": 2340,
    "result_quality": "verified",
})
```

#### L2：决策面定义（深度集成）
写一个 YAML 决策面文件 + 可选的自定义指标计算器。

**集中注册表机制：** 所有决策面 YAML 文件统一存放在 `data/eval/modules/` 目录下，eval engine 通过一个 `_load_decision_surfaces()` 函数集中加载，而非各模块自行注册。加载失败的文件被跳过并记录告警，不影响其他已加载的决策面：

```python
def _load_decision_surfaces():
    """集中加载所有决策面定义。单个文件加载失败不影响整体。"""
    surfaces = {}
    for yaml_file in (DATA_DIR / "modules").glob("*.yaml"):
        try:
            surfaces[yaml_file.stem] = yaml.safe_load(yaml_file.read_text())
        except Exception as e:
            emit_event("eval.decision_surface_load_failed", {
                "file": str(yaml_file), "error": str(e)
            })
    return surfaces
```

评估系统根据已加载的决策面自动为该模块生成指标、告警、建议。

### 2.6 与现有模块的具体对接

#### review_agent → 决策链
在 `review_agent.run_review()` 产出 findings 后追加 `emit_event("review_agent.finding", ...)`。eval engine 新增 `_ingest_review_findings()` 将 finding 转入决策链。

#### 知识管线 → 决策链
新增 `knowledge_health_check()` 函数（在 eval engine 中），每日检查 ChromaDB 同步时间、知识条目数对比、孤立标签等。不修改 `knowledge_sync.py` 本身——eval 引擎定期去查询它。

#### doc_indexer → 决策链
新增 `_check_error_patterns()` 函数，扫描 `知识库/错误与修正与优化/` 下的历史错误文档，匹配当前系统状态。发现相似模式 → 发射预警事件。

#### 前端行为追踪 → 决策链
在关键 JS 函数中追加 `fetch('/api/eval/beacon', ...)`，后端接收后 `emit_event("ui.interaction", ...)`。极简数据：事件类型 + 时间戳。

> **透明度声明：** Dashboard 底部必须显示可见文字："本页面的交互行为（点击、展开、切换面板）将被匿名记录，用于优化评估系统的可用性。不会追踪任何个人身份信息。"

### 3.2 里程碑

#### M1：事件管道泛化 — 双轨并行（预计 3-5 个 commit）

**目标：** 新增 `emit_event()` 统一入口（用于所有新增事件来源），但三条现有核心埋点路径保持硬编码不变。

**架构决策（双轨并行过渡）：**

```
第一轨（保持硬编码）：deepseek_client._record_llm_span()
                     Flask before_request/after_request hooks
                     agent_service._record_tool_span()
  → 这三条路径覆盖了 100% 的 LLM/HTTP/Tool 追踪，Phase 1-4 充分验证
  → M1 不修改它们，确保核心数据采集零风险

第二轨（新增 emit_event）：Git 提交、知识摄入、前端行为、用户反馈等所有新增来源
  → 统一调用 emit_event()，不各自硬编码
  → emit_event() 内部写入 events.jsonl 并委托现有 _record_span() 到同一存储
```

**为什么不是现在统一：** 如果 emit_event() 在 M1 引入时有 bug（非 Flask 上下文中崩溃、schema 校验失败导致写入中断），只会影响新增来源，不会导致 LLM/HTTP/Tool 核心追踪静默丢失。等 emit_event() 经过 M1-M3 验证稳定后，M4-M5 再考虑迁移三条核心路径。

## 4. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 事件管道过度设计 | 接入门槛不降反升 | 严格保持 L1=3 行代码的约束，超过就简化 |
| 追溯链 ID 链断裂 | 追溯变成假追溯 | M2 验收时逐环验证 ID 可追溯性 |
| 追溯链篡改未被检测 | 手动修改引用导致假追溯 | chain_hash 完整性校验，元评估抽样检查 |
| 无限细分导致指标爆炸 | 系统运转缓慢 | 细分必须通过三触发器审批，且有停止条件 |
| 元评估叠元失控 | 无限递归 | L2 硬终止于人工 |
| L2 与 L1 线程共崩溃 | L1 崩溃时 L2 一起死，无人看到红灯 | L2 独立 Timer + 独立日志 + stdout 警告 |
| 与现有模块对接失败 | review_agent 等拒绝接入 | 不修改核心逻辑，只在外层加 emit_event，不影响原有行为 |
| 决策面 YAML 碎片化 | 散落的 YAML 文件难以维护 | 集中注册表 `_load_decision_surfaces()`，单文件失败不影响整体 |
| 前瞻性检测器拖垮后台 | M5 扫描任务 O(n²) 耗时过长 | 低频运行（每日/每周）+ 每个 M 性能基线条验收 |
| 前瞻性扫描资源耗尽 | 巨型文件/海量文件导致后台阻塞 | 硬性资源限制（1MB/1000文件/30s），超限记 errors[] |
| 前瞻性水源噪音过大 | 探测卡过多变成垃圾 | 每种探测卡初始上限=5条，30天自动过期 |
| emit_event 数据注入 | 前端/外部模块向事件流注入伪造事件 | event_type 白名单校验 + beacon 鉴权 + 字段长度限制 |
| 前端追踪隐私泄露 | beacon 采集鼠标/键盘/剪贴板数据 | JS 端字段白名单 + 后端双重过滤，限定事件类型+面板ID |
