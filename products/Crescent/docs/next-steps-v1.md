## 0. 总裁战略判断: 信任鸿沟

五位专家审查意见共同指向一个核心问题——**系统正站在"信任鸿沟"的边缘:**

- LLM Judge 从未被真实调用——交叉验证的设计正确，但它从未运行过
- 元评估准确性未校准——它发现了 `eval-main.js` 的违规，但其他判断是否准确，未知
- 审计日志不记录失败尝试——无法回答"是否有人在尝试攻击系统"
- 知识库路径硬编码——静默失效风险存在但修复承诺不明确

**这些不是功能缺失，是信任缺失。** 更危险的是，团队在潜意识里把"设计正确"等同于"已完成"——但一个从未被真实调用的机制，不是"已完成"，是"未验证"。

**战略判断: 在信任缺失被修复之前，不允许任何新功能的开发。**

**战略节奏: 先验证，再进化。这是不可违背的。**

### P0-2: 审计日志覆盖鉴权失败路径

**问题:** `_check_admin()` 鉴权失败返回 403，不写入 `audit.jsonl`。无法回答: 过去 24h 有多少未授权尝试？来自哪个 IP？是否有暴力破解模式？安全审计师指出这给了攻击者一个"隐身斗篷"。

**完成标准:**

- [ ] 条目包含全部必填字段

- [ ] 成功操作的审计日志不受影响

**涉及文件:** `routes/api_eval.py` (`_check_admin`), `eval_store.py`

**问题:** `evaluate_knowledge_base()` 路径不存在时静默返回空列表 → Dashboard 显示 0.0。审计AI警告:"静默失效是安全系统最危险的失败模式。"

5. **subprocess 编码** — `errors='replace'` 后检测替换字符数，>0 时记录警告事件到 `audit.jsonl`

**完成标准:**
- [ ] 知识库路径移至 `config.py` 常量
- [ ] 路径不存在 → 显式错误信号（非空列表）
- [ ] 前端区分"评估不可用"和"评分 0.0"

## 5. Phase 5 验收标准（强制执行）

| # | 标准 | 含义 |
|---|------|------|
| 1 | **"从未被调用"即"未完成"** | 设计正确但未经验证的机制，不能标记为完成 |
| 2 | **"静默失效"即"未完成"** | 可能因外部条件变化而失效的函数，必须用显式信号表达失效 |
| 3 | **"审计日志覆盖所有尝试"** | 鉴权或状态变更操作的成功和失败路径均写入审计日志 |
| 4 | **"拆分即安全"** | JS 模块 >300 行或有明确职责边界可提取时，编码前完成拆分 |

## 6. 战略方向

Phase 5 是"减速加固"阶段。目标是让评估系统从"设计正确"走向"运行可信"。

当 P0 和 P1 项全部完成，我们将拥有一个经过真实验证、边界清晰、审计完整的基线。届时，归零推演中被标注的前提条件——"评估结果经过交叉验证且自指健康"——才能被满足。

**这个前提被满足之前，任何"自动回滚"、"自动修复"、"阈值自调整"、"指标自动发现"的自进化功能都不允许启动。先验证，再进化。**
