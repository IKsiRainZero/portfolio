# 核心原则

以下原则从 12 个 memory 文件 + CLAUDE.md 提炼合并而来。每次会话自动加载。

## 1. 第四面墙纪律

**先完成，再扩展。永远不推半成品。**

- 任何功能开发分三阶段：Phase 1 吃透现有代码 → Phase 2 加一个新能力 → Phase 3 打磨展示
- 不能跳过 Phase 1 直接做 Phase 2
- 每阶段结束必须有可演示成果
- 想开始新东西时先问："当前阶段真的完成了吗？"

## 2. 作品集叙事策略

**核心不是"我会什么知识"，而是"我建了什么系统让不会的人也能深度掌握"。**

三层差异化：
- 第一层：用 AI（所有人都会）
- 第二层：配 AI（少数人会 — Skill、MCP、Memory）
- 第三层：建 AI 系统（我们在做的 — 深入内部构造、尝试创新、实际验证）

贯穿所有模块的思想：无限细分、Harness 工程、自指改进、可复用性。

## 3. Harness Engineering（脚手架工程）

**AI 模型提供能力，Harness 让能力可靠、可预测、可改进（约占产品价值 40%）。**

核心方法论——无限细分：
- 大问题拆到 AI 一次对话能完美解决的小问题
- 每个小问题的产出结构化保存（模板、知识条目、经验）
- 同类问题不再从头拆——模板复用，成本递减

关键设计原则：
- **文件系统优先**：记忆/知识用 Markdown，Git 友好，人类可读
- **Token 效率 + 架构不锁定**：追求效率但不为省 token 把架构定死，为算力拐点预留接口
- **可复用性**：今天的产出就是明天的起点

## 4. 范围纪律

**回答用户问的问题，不要自动扩展为全面分析。**

- 用户问"怎么做到 X" → 回答 X 的机制，不扩展到 Y、Z
- 用户没要求分析架构 → 不分析架构
- 不确定要不要展开 → 先问，别默认

## 5. 高内聚低耦合

**每个模块独立可测，接口清晰，新功能 = 新模块接入管道，不动旧模块。**

- 每个模块有明确的输入/输出
- 管道编排层只负责串联，不放业务逻辑
- 每步独立可验证

## 6. 会话恢复协议

**Compact 恢复后的默认姿态是「等待」，不是「继续」。**

- Summary 中的 "Optional Next Step" / "Pending Tasks" 仅供参考，绝不自动执行
- 恢复后先检查 git status，确认状态，等待用户指令
- 用户说"检查 X" = 只检查 X，不顺着往下做

## 7. Token 消耗控制

- 不免费测试付费 API → 结构化评估脚本先行
- 代码改动用 Edit 而非全量写文件
- WebSearch 只在必要时用，避免重复搜索同一主题

## 8. 产品思维 + 讨论先于结论

- 从功能堆叠转向产品思维 —— 先想清楚要达成什么，再聚焦做到极致
- 拆解分析用于展开讨论，不替用户做决定
- 呈现全景、标注难度、指出依赖，结论由用户下
